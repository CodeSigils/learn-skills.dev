Úselo al crear o modificar un plan de prueba/plan de verificación de control de calidad: qué probar, a qué nivel, con qué criterios realizados y los casos a ejecutar. Guía el MÉTODO, no el esquema: derivar cada caso de un comportamiento/AC de especificación de característica o operación/error de especificación de API (nunca inventar uno); los niveles funcionales que garantiza el proyecto; Dimensionamiento del catálogo PONDERADO POR RIESGO (BVA/equivalencia/tabla de decisiones/transición de estado/por pares, no el producto cruzado); una taxonomía no funcional (perf/seguridad/accesibilidad WCAG 2.2 AA/compat/i18n) cada una con un objetivo numérico cuando esté justificado; casos de umbral de métrica en un conjunto de datos con nombre para comportamiento probabilístico/ML; y modificarlo como un delta versionado con selección de regresión de impacto+riesgo, a una barra donde un evaluador lo ejecuta sin preguntas, con cada comportamiento rastreado. Redacta con una herramienta de plantilla + investigación profunda; consume fuentes entregadas (feature-spec/api-spec/PRD/NFR), nunca una página en blanco. Especifica los casos, no los guiones; ni el runbook, ni el contrato de comportamiento, ni la revisión de uno.
