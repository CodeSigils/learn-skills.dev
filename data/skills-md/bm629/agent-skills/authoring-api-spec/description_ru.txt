Используйте при разработке спецификации API — инженерный контракт поверхности API: операции/конечные точки, схемы запроса + ответа (поля, типы, обязательные/необязательные, ограничения), аутентификация, полная модель ошибок, нумерация страниц/ограничения скорости, управление версиями и рабочие примеры. Помогает производителю использовать МЕТОД, а не схему: рендеринг контракта в стиле проекта (OpenAPI для REST, SDL для GraphQL, proto для RPC), ввод каждого поля, перечисление СЛУЧАЕВ ОШИБОК (а не только счастливый путь), отслеживание каждой операции до поведения, определяемого спецификацией функции, и ссылка на модель данных, а не ее переопределение - до панели, где клиент может вызывать каждую операцию, а сервер может реализовать ее из контракта. один. Состоит из отдельного инструмента шаблонов API-спецификаций и возможностей глубокого исследования. Предполагается, что исходная спецификация функций (+ документация по архитектуре + модель данных, если она присутствует) — никогда не пустая страница. Ни модель данных персистентности, ни ссылка на API, ориентированная на потребителя, ни реализация, ни проверка готовой спецификации API.
