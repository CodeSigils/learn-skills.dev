Use when authoring an end-user guide — the consumer-facing help the (typically non-technical) person USING a product reads to accomplish their goals: a getting-started tutorial, task-oriented how-to guides, conceptual explanation, an end-user feature/configuration reference (features, settings, CLI commands — not the HTTP API), and troubleshooting/FAQ. Guides the METHOD, not the outline: deriving one how-to per user goal from the handed-in upstreams (never inventing steps), keeping the four Diataxis modes distinct, and holding every step accurate to the actual product behavior. Composes with a separate user-guide template tool (which supplies the section structure) and a research capability. Assumes the handed-in upstream docs (typically a feature-spec + user-flows + wireframes) — never a blank page. Not for the developer-tool adoption narrative (a separate developer-guide), not for the HTTP/SDK endpoint catalog (a separate api-reference), and not for reviewing a finished user guide.
