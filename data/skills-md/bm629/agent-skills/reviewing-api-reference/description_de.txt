Wird verwendet, wenn eine veröffentlichte, verbraucherorientierte API-Referenz überprüft/beurteilt wird, von der aus ein integrierender Entwickler eine API aufruft und entscheidet, ob er daraus integrieren kann. Ein Tor, kein Authoring. Beurteilt anhand einer aus einer einzigen Quelle stammenden 11-Bedingungsleiste für Benutzerfreundlichkeit + Vertragskonsistenz: Erste Schritte + Authentifizierung, Erreichen eines ersten Anrufs; Jeder API-Spezifikationsvorgang (einschließlich Ereignisse/Webhooks) wird mit Zweck + typisierten Parametern + einem ausgearbeiteten Beispiel + Fehlern dokumentiert. Fehler erstklassig; Ratenbegrenzungen + Seitennummerierung ggf. dokumentiert; Versionierung + Veraltung/Verfall angegeben; Die Referenz stimmt mit der eingereichten API-Spezifikation überein (keine Drift, kein fabrizierter Endpunkt – die Tragfähigkeitsprüfung); Proben lauffähig; Eine Änderung wird erneut mit dem geänderten Vertrag synchronisiert. Gibt genau „URTEIL: genehmigen|überarbeiten“ plus umsetzbare Ergebnisse aus; genehmigt eine proportional große Referenz und überarbeitet eine benannte Lücke. Ich habe es nicht verfasst, nicht das Endbenutzer-Benutzerhandbuch, nicht den Entwickler-Einführungsleitfaden, nicht die technische API-Spezifikation (Reviewing-API-Spezifikation).
