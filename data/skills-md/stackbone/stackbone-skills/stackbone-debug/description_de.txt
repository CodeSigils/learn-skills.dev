Verwenden Sie diese Fähigkeit, wenn Sie einen Fehler, einen Ausfall oder ein unerwartetes Verhalten in einem Stackbone-Arbeitsbereich untersuchen – ein Deep Agent oder ein dauerhafter Workflow, der lokal unter „stackbone dev“ ausgeführt wird, oder eine Installation, die in einer Cloud/einem Selbsthost bereitgestellt wird. Deckt SDK-Fehler ab ({ data, error }-Umschlagcodes aus dem Katalog, der vom Umgebungs-„Stackbone“-Client zurückgegeben wird), HTTP 4xx/5xx von der Steuerungsebene, dauerhafte Ausführungsfehler und Zeitüberschreitungen, „workflow_input_invalid“ (ein Workflow-Start, dessen Eingabe das deklarierte Schema nicht erfüllt hat), HITL, das auf beiden Ebenen hängen bleibt (ein Workflow, der auf einem „requestApproval()“-Gate geparkt ist, oder ein Agent, der auf einem Tool mit „unterbrochen“ wird `interruptOn`), dauerhafte Sitzungsprobleme (Speicher bleibt nicht erhalten, weil `x-stackbone-session` nicht gesendet wurde oder das Checkpointer-Paket fehlt), langsame Datenbankabfragen/fehlende Indizes/pgvector-Nichtübereinstimmungen, Fehler bei der Entschlüsselung von Geheimnissen, Connector-Aktionsfehler über `stackbone.connection(id)` (mehrdeutige/nicht autorisierte Verbindungen), Veröffentlichungs-/Build-Fehler (SDK inlined, native dep), Tierkontingent überschrittene Antworten und Situationen mit OpenRouter-Ratenbegrenzung/Abrechnungspause. Auslöser bei Anfragen wie: Mein Agent funktioniert nicht, warum ist dieser 500, dieser Lauf hängt, der HITL-Posteingang ist leer, aber der Lauf ist angehalten, der Agent hat die Konversation vergessen, der Workflow hat meine Eingabe abgelehnt, die Veröffentlichung ist fehlgeschlagen, warum erhalte ich 402, warum ist mein Connector-Aufruf mehrdeutig, der Modellaufruf gibt keine Antwort zurück. Die Fertigkeit leitet die Ausführung von Diagnosebefehlen; Es werden keine Korrekturen vorgeschlagen. Sobald Sie die Ursache gefunden haben, wechseln Sie zurück zum Stackbone- oder Stackbone-Cli-Skill, um die Korrektur zu implementieren.
