Führen Sie eine einzelne unabhängige Gremiumsprüfung eines schriftlichen Plans (einer Entwurfs-/Implementierungs-Markdown-Datei) durch, bevor Code geschrieben wird. Verwenden Sie diese Fähigkeit immer dann, wenn der Benutzer „Panel-Plan“/„Panel-Plan“, „Meinen Plan vom Panel überprüfen lassen“, „Diesen Plan vom Panel überprüfen lassen“, „Zweitmeinungen zu diesem Plan einholen“, „Die Meinung des Panels zu diesem Plan einholen“, „Eine Planüberprüfung auffächern“ oder eine ähnliche Formulierung verlangt, in der eine unabhängige Überprüfung eines Plans durch mehrere Agenten verlangt wird. Der Plan wird an mehrere lokale CLI-Coding-Agenten (Codex, Claude, Opencode) verteilt, jeder in einem neuen, nicht interaktiven Unterprozess ohne gemeinsamen Status, der den Plan und das Repository, auf das er abzielt, schreibgeschützt liest und dann ihre Ergebnisse (Lücken, falsche Annahmen, undurchführbare Schritte, Risiken) und offene Fragen in einem Bericht zusammenfasst. Dies ist das Planungszeit-Analogon der Panel-Überprüfung (die den ausgelieferten Code überprüft). Es handelt sich um EINEN Durchgang, bei dem der Plan NICHT bearbeitet wird. Für die Konvergenz der Iterate-Edit-Re-Review-Schleife verwenden Sie die Panel-Plan-Schleife. NICHT zur Überprüfung eines Codeunterschieds oder einer PR (d. h. einer Panel-Überprüfung) verwenden oder wenn der Benutzer in dieser Sitzung lediglich den Plan selbst kritisieren möchte.
