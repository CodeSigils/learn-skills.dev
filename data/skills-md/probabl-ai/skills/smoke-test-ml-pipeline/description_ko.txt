ML 실험을 위한 스모크 테스트 계약을 소유합니다. 즉, 실제 '데이터/' 소스의 일부에 실험의 학습자를 맞추고 의도적으로 **사전 버퍼 없음**을 전달하는 *분리된* 부분을 예측하는 구성별 진단 작은 pytest입니다. 어설션은 구조적입니다. 예측 수는 예측 그리드의 행 수와 동일해야 합니다. 로드 후 기능을 수행한 후 분할하는 파이프라인은 예측 슬라이스의 콜드 스타트 ​​행을 자동으로 삭제하고 행 개수 불일치로 인해 테스트가 실패합니다. X를 초기에 표시하고 기능 단계에서 업스트림 기록 노드를 참조하는 파이프라인은 간단하게 통과됩니다. 스모크 테스트는 `build-ml-pipeline`의 X 마커 배치 규칙에 대한 실행 가능한 증거입니다.
TRIGGER 언제: 'test-ml-pipeline'이 승인된 실험에 대한 연기 테스트를 작성하기 위해 여기로 파견되었습니다. `pytest 테스트/smoke/`가 행 개수에 실패합니다. 사용자가 "스모크 테스트가 왜 실패하나요?"라고 묻습니다. `build-ml-pipeline`의 파이프라인 편집에는 실행 가능한 증명이 필요합니다. 실험 스크립트는 파이프라인 모양을 변경하고 일치하는 연기 테스트를 다시 방문해야 합니다.
다음의 경우 건너뛰십시오: 설계 노트가 존재하지 않거나 아직 승인되지 않았습니다(`iterate-ml-experiment`로 경로 지정). 사용자가 회귀 테스트 또는 스키마 불변에 대해 묻습니다(해당 항목이 있으면 `regression-test-ml-pipeline` / `distribution-test-ml-pipeline`으로 경로 지정). 문제는 예측 시간 정확성(`evaluate-ml-pipeline`으로 경로 지정)이 아니라 CV 지표의 *해석*입니다.
사용 방법: 일치하는 실험의 `journal/NN_*.md` 및 `experiments/NN_*.py`를 먼저 읽고 파이프라인의 소스 바인딩을 이해하세요(`build_learner`에서 기대하는 env-dict 키는 무엇입니까?). 그런 다음 **실제 `data/` 소스**에서 두 개의 env-dict(train env와 예측 env)를 구성하여 예측 env가 *우리가 예측하려는 행만* 전달하고 *사전 버퍼는 없음*을 전달합니다. 확실한 주장은 예측 개수가 예측 환경 행 개수와 정확히 일치한다는 것입니다. 부드러운 주장은 연기 세트의 MAE가 '3 × CV_mean'(또는 작업에 적합한 아날로그) 내에 있다는 것입니다. **디자인 노트를 작성하거나 CV를 실행하지 마십시오. 이는 다른 기술의 작업입니다.**
