The expect/actual mechanism in Kotlin Multiplatform — when to use it, when NOT to, and how to do it correctly. Covers: the four categories that genuinely warrant expect/actual (platform APIs, platform types, performance-critical code, SDK integration), the common-first rule that prefers a pure `commonMain` implementation before abstractions, the interface-injection alternative that handles most cases better, the "actual everywhere" anti-pattern, typealias actual for platform types, @ObjCName for clean Swift API surfaces, and Kotlin/Native memory considerations. Zero new dependencies.
