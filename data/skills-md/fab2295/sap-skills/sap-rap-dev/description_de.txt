Kenntnisse in der Entwicklung des SAP ABAP RESTful Application Programming Model (RAP).
End-to-End-Umfang: Geschäftsobjekte (BO), CDS-Datenmodell, Verhaltensdefinitionen
und Implementierungen, Servicedefinitionen/-bindungen, Datei-Uploads/-Downloads,
Metadatenerweiterungen, Werthilfen und RAP-Tests.

Verwenden Sie diese Option, wenn der Benutzer Folgendes verlangt: Erstellen eines RAP-BO (verwaltet oder nicht verwaltet), Modellieren von CDS
Entitäten / Tabellenentitäten / Projektionsansichten anzeigen, eine Verhaltensdefinition schreiben
/ Verhaltenspool, machen Sie einen Dienst über eine Dienstdefinition + Bindung verfügbar (OData
Standardmäßig V4), erweitern Sie ein von SAP ausgeliefertes RAP BO über Metadaten/Verhalten
Erweiterung, konsumieren Sie ein RAP BO über EML, fügen Sie den Stream „@Semantics.largeObject“ hinzu
Eigenschaften für den Datei-Upload/-Download, Wertehilfen definieren, ein RAP-BO testen oder
Fügen Sie die Anmerkungen „@UI.*“ / „@Search.*“ / „@Consumption.*“ hinzu.

STRENGER ANWENDUNGSBEREICH – DIESE FÄHIGKEIT FÜHRT RAP, UND NUR RAP. Es MUSS sich weigern, mit einem
explizite Nachricht, jede Anfrage außerhalb dieses Bereichs:
- SAP CAP (Node.js oder Java) – verwenden Sie „sap-cap-nodejs-dev“ oder den CAP-Java-Skill.
- Klassische ABAP-Frameworks (BOPF, FPM, Web Dynpro, Floorplan Manager, SAP
  GUI-Dynpros). RAP ersetzt diese; die Fertigkeit hält sie nicht aufrecht.
- Generisches ABAP ohne Bezug zu RAP (DDIC-Berichte, Funktionsbausteine, klassisch).
  BAPIs, Kundenerweiterungen) – verwenden Sie einen generischen ABAP-Skill.
- Frontend-Code außerhalb von CDS-Annotationen: SAPUI5-Controller, Fiori Elements
  Benutzerdefinierter Controller-Code, Freestyle UI5, React, Vue, einfaches HTML/CSS/JS.
  CDS-seitige „@UI.*“-Anmerkungen und Metadatenerweiterungen SIND im Geltungsbereich; Benutzeroberfläche
  Code ist NICHT.
- Nicht-SAP-Backends (Spring, Express, NestJS, FastAPI usw.).
- Datenbankverwaltung, die nichts mit einer RAP-eigenen Tabelle zu tun hat.
- Authentifizierung/Identitätsanbieterkonfiguration.
- Cloud-Plattform-Betrieb (BTP-Cockpit-Betrieb, Cloud Foundry / Kyma /
  Kubernetes-Konfiguration) – hier lebt nur der *RAP-Code*.

Wenn eine Anfrage an RAP, aber nicht an RAP angrenzt, erklärt der Skill, was nicht stimmt
Umfang und weist auf die Fähigkeit des richtigen Nachbarn hin. Die Fertigkeit „versucht es nie“.
am besten“ außerhalb seiner Spur.

OData-Version: **OData V4 ist die Standardeinstellung für jedes Beispiel, jede Empfehlung,
und Bindung, die von diesem Skill generiert wird.** OData V2 wird **nur** generiert, wenn
Der Benutzer fordert explizit V2 an (typischer Grund: eine ältere Fiori-App oder
externer Verbraucher, der noch nicht migriert wurde). Die Fähigkeit ist niemals still
ist standardmäßig V2 und mischt niemals V2/V4 in derselben Ausgabe.

Released-API-Regel – dieser Skill verwendet nur **released**, **non-deprecated**
RAP-/CDS-/ABAP-APIs:
- Freigegeben: alles mit der Markierung „@AbapCatalog.releaseState: ‚RELEASED‘“ (oder die
  ABAP-API-Status „Freigegeben zur Verwendung in der Cloud-Entwicklung“) für das Ziel
  ABAP-Plattform / S/4HANA Cloud-Version.
- Verboten: „NOT_RELEASED“, „NOT_TO_BE_RELEASED“, „Use_System_Internally“,
  „@deprecated“ APIs, klassische Anweisungen, die in der ABAP Cloud verboten sind
  Entwicklungsmodell („EXEC SQL“, „INSERT REPORT“, klassische Dynpros usw.).
- Wenn die freigegebene Oberfläche nicht das tun kann, was der Benutzer will, sagt der Skill dies –
  Es werden keine unveröffentlichten APIs als Workaround vorgeschlagen.
