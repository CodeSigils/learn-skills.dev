Traçabilité bidirectionnelle entre les commits et les tickets. (A) Lorsque vous validez une modification, assurez-vous que le message de validation porte le numéro de ticket/élément de travail – dérivez-le des mots de l'utilisateur, du nom de la branche ou de la tâche en cours, demandez s'il est inconnu (un hook commit-msg est fourni mais installez-le uniquement sur demande explicite). (B) Lorsque l'utilisateur demande POURQUOI le code est tel qu'il est : "pourquoi cela a-t-il été modifié", "qui a décidé cela", "ce code en dur est-il intentionnel", "ทำไมถึงแก้อันนี้", "มีเหตุผลป่าว" - tracez la ligne via git blâme/log jusqu'au commit, extrayez le numéro de ticket du message, récupérez le ticket à partir du tracker (Azure DevOps, GitHub Issues, JIRA), Y COMPRIS le téléchargement et la lecture des images jointes (les exigences ne résident souvent que dans une capture d'écran annotée) et répondez avec une preuve de commit + ticket. Déclenchez-vous sur n'importe quelle demande de validation dans un dépôt avec ticket, sur "installer le crochet de validation" et sur toute question pourquoi ce code ressemble-t-il à ceci / changer d'archéologie - même lorsque l'utilisateur ne mentionne pas de tickets.
