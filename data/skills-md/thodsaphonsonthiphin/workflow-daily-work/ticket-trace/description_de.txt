Zweiseitige Rückverfolgbarkeit zwischen Commits und Tickets. (A) Stellen Sie beim Festschreiben einer Änderung sicher, dass die Festschreibungsnachricht die Ticket-/Arbeitselementnummer enthält – leiten Sie sie aus den Worten des Benutzers, dem Zweignamen oder der aktuellen Aufgabe ab und fragen Sie, ob sie unbekannt ist (ein Commit-Msg-Hook ist im Lieferumfang enthalten, installiert ihn jedoch nur auf ausdrückliche Anfrage). (B) Wenn der Benutzer fragt, WARUM der Code so ist, wie er ist – „Warum wurde das geändert“, „Wer hat das entschieden“, „Ist dieser Hardcode beabsichtigt“, „Ungültig“, „มีเหตุผลป่าว“ – Verfolgen Sie die Linie durch Git Blame/Log bis zum Commit, extrahieren Sie die Ticketnummer aus der Nachricht, rufen Sie das Ticket vom Tracker ab (Azure DevOps, GitHub Issues, JIRA), EINSCHLIESSLICH dem Herunterladen und Lesen angehängter Bilder (Anforderungen werden oft nur in einem kommentierten Screenshot angezeigt) und antworten Sie mit Commit + Ticketbeweis. Wird bei jeder Commit-Anfrage in einem Repo mit Ticket, bei „Install Commit Hook“ und bei jeder Frage „Warum ist dieser Code so?“ bzw. „Änderungsarchäologie“-Frage ausgelöst – auch wenn der Benutzer keine Tickets erwähnt.
