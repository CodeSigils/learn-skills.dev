# test-case-generator

资深 QA 测试用例生成工作流。5 步强制串行，每步输出后**必须暂停**等待用户确认或调整，再进入下一步。

## 触发条件

满足任一即应用：

- 用户粘贴/描述一段产品需求并要求"写测试用例 / 测试点 / 用例评审 / QA 覆盖"
- 用户提到「测试用例」「测试点」「需求拆解」「9 维度」「测试覆盖度」
- 用户在已有需求/Spec 上下文里要求"帮我测一下"或"做用例"

## 全局约束

- **回复语言**：中文
- **每步必须暂停**：禁止一次性把步骤 1~5 全部跑完；每完成一步必须 append 下方的「暂停确认块」并停止生成
- **步骤 1 拆为 1a + 1b**：先输出拆解 + 歧义清单（1a），等用户回应歧义后自动进 1b 输出定稿需求
- **基于上一步输出**：步骤 2~5 不要求用户重新粘贴，直接引用本会话中前序输出
- **风格**：每条 ≤ 一句话；测试点必须含具体数据；预期必须可验证；禁用"测试 xxx / 正常显示 / 超长字符串"等抽象词
- **禁止脑补**：不假设需求外业务，疑点一律放到歧义清单
- **最终交付**：步骤 3 起所有用例以 markdown 表格输出，可直接复制粘贴到 Excel / 飞书多维表格 / Numbers

## 开场流程（收到需求后第一步）

如果用户尚未提供以下 3 项，**先提问补齐**，不要直接开始步骤 1a：

1. **测试平台**（必填）：iOS App / Android App / Web / 微信小程序 / H5 / 桌面 / API / 多端组合
2. **是否多端**：是 / 否
3. **需求文本**：未提供则索取

集齐后，宣布"准备进入步骤 1a：需求分析"并立即开始。

## 暂停确认块（每步输出末尾必须附带）

```
已完成 [步骤 X：阶段名]

回复「确定」进入下一步 / 「停止」结束 / 或直接说改什么
```

特殊步骤的暂停规则在下面各步单独说明。

---

## 步骤 1a：需求分析

按 3 部分输出（**不输出"澄清后的需求"——那是步骤 1b 的事**）。

**▼ 第一部分：需求理解**

1. **【显式功能点】**

   **颗粒度约束**：
   - 功能 X = 测试视角下的最小可独立验证模块，**不是需求原文的句子分割**
   - 每条功能大致对应 5~15 条测试用例；输出 3~7 条即可
   - 反例：「功能 2：兑换成功弹 toast」（这是 UI 反馈，不是独立模块）
   - 正例：「功能 1：兑换成功完整流程（输入 → 提交 → 反馈 → 列表更新）」

   输出格式：`功能 1：xxx` / `功能 2：xxx` ...

2. **【隐含约束】** 需求没明说但明显存在的（唯一性？大小写？时区？精度？并发？权限？）
3. **【依赖与边界】** 涉及的外部系统/角色/状态/三方服务
4. **【风险点 TOP3】** 最容易出 bug 的地方

**▼ 第二部分：歧义清单（≥ 3 条，markdown 表格输出）**

**列结构**：`# | 需确认 | 可能方向（仅参考） | 为什么重要`

**"可能方向"列要求**：

- 用 A/B/C 列举 2~4 种合理可能性
- **仅供参考，不作为默认值**——QA 不替产品决策
- 一条歧义只包含一个产品决策；多决策必须拆成多条
- 用户可选 A/B/C，也可写自己的答案，或回复"待 PM 确认"

**输出示例**：

| # | 需确认 | 可能方向（仅参考） | 为什么重要 |
|---|---|---|---|
| 1 | 评分是否必填？ | A. 必填<br>B. 非必填默认 5 星<br>C. 非必填不允许 0 星 | 若非必填，需补 0 星可发布用例；UI 校验逻辑反向 |
| 2 | 文字评价计数规则？ | A. Unicode 码点 1 个 = 1 字<br>B. 中文 1 字、英文 0.5 字<br>C. UTF-8 字节数 | 计数错误会让 ≥10 字校验类用例全部失效 |

**▼ 第三部分：识别【测试对象】（结合平台特性）**

- UI 元素：输入框 / 按钮 / 列表 / 弹窗 / Tab / ...
- 数据字段：手机号 / 订单 ID / 金额 / Token / ...
- 业务动作：提交 / 查询 / 上传 / 支付 / 退款 / ...
- 平台特化对象（按声明的平台补充）：
  - App：推送通知 / Deep Link / 权限弹窗 / ...
  - Web：浏览器返回按钮 / Tab 切换 / ...
  - 小程序：启动场景 / 分享卡片 / ...
  - API：接口 / 鉴权流程 / ...

每个对象一行：`对象名称 | 类型 | 关联功能编号`

**内容安全强约束**：

识别到以下对象时**必须**在对象名称后追加内容安全标注，否则步骤 2 会漏测：

- 文字输入类（评价 / 评论 / 留言 / 昵称 / 文章 / 消息） → 追加 `[需测：敏感词 / 富文本注入]`
- 图片上传类（头像 / 商品图 / 评价图 / 动态图） → 追加 `[需测：敏感图识别 / 恶意文件]`
- 视频上传类 → 追加 `[需测：敏感内容审核 / 时长大小限制]`
- 用户生成 URL 类（链接分享 / 个性签名带链接） → 追加 `[需测：恶意链接 / 钓鱼站]`

示例：`评价文字输入框 | 输入框 | 功能 1 [需测：敏感词 / 富文本注入]`

**步骤 1a 特殊暂停规则**：

```
已完成 [步骤 1a：需求分析]

请逐条回答歧义清单 1~n，如「1 选 A / 3 选 B 但上限 200 字 / 5 待 PM 确认」。
禁止「全部接受」——QA 不替产品决策。
不确定的请明确回复「n 待 PM 确认」，定稿中会显式标注。

回答后自动进入步骤 1b。
```

## 步骤 1b：澄清需求定稿

**触发**：用户对步骤 1a 的歧义清单给出逐条答案后**自动进入**（不需用户说"继续"）。

**输出**：基于用户对每条歧义的答案，重写一份明确的需求规格作为步骤 2 的输入。

**开头必须显式声明**：「以下规格基于你的决策——1=X、2=Y、3=待 PM 确认...」，让用户一眼看到每条歧义的最终状态。

**未确认条目处理（关键）**：

- 用户答案 = "n 待 PM 确认" 的条目，**不写具体值**
- 在规格对应位置用 `[待 PM 确认（条目 n：影响 xxx）]` 显式标注
- 示例：「文字评价上限 [待 PM 确认（条目 3：影响超长文本边界用例）]」
- 步骤 2 提取测试点时：对待确认项**跳过具体边界值用例**，但保留"功能存在性"测试（如未确认上限不影响"必填校验"类测试）

**步骤 1b 暂停**：按通用确认块格式，引导用户「确定」进入步骤 2。

## 步骤 2：测试点提取

基于步骤 1b 的【澄清后需求】和步骤 1a 的【测试对象清单】，对每个测试对象沿 9 维度展开。

**9 维度**：

1. 业务规则：合法集 vs 非法集
2. 数据类型：数字 / 字母 / 中文 / 符号 / Emoji / 控制字符 / 混合 / Null / **敏感词（违禁词/政治/辱骂）** / **富文本注入（HTML/Markdown/脚本片段）**
3. 长度边界：0 / 1 / min-1 / min / min+1 / max-1 / max / max+1
4. 格式：大小写 / 前后空格 / 全半角 / 转义字符 / 不可见字符 / 编码
5. 状态：空 / 有值 / 只读 / 禁用 / loading / 已锁 / 已过期
6. 交互：输入 / 粘贴 / 删除 / 快速连点 / 输入法切换 / 语音 / 手势
7. 时序：连续 / 间隔 / 超时 / 同时 / 乱序
8. 环境（按声明平台展开）：
   - 8a. 网络：WiFi / 4G / 5G / 弱网 / 无网 / 切换 / VPN
   - 8b. 平台特化：
     - Web：浏览器矩阵 / 版本 / 缩放 / 快捷键 / Tab / 隐身 / Cookie
     - H5：移动端 viewport / 软键盘弹起 / 系统返回键 / 横竖屏 / 网络切换 / 输入法联想
     - iOS App：系统版本 / 机型 / 刘海屏 / 安装更新 / 杀进程 / 权限 / 推送 / Deep Link
     - Android App：版本 / 厂商 / 分屏 / 折叠屏 / 后台限制 / 权限 / 推送通道
     - 小程序：客户端 / 启动场景 / 生命周期 / 分包 / 授权 / 跨端跳转
     - 桌面：OS / 多屏 / 窗口状态 / 系统集成 / 电源
     - API：协议 / 鉴权 / 响应码 / 并发 / 限流 / 字段缺失
9. 角色：新用户 / 老用户 / 未登录 / 被锁 / 权限 / 跨端登录

**内容安全特化测试点**（针对步骤 1a 标注 `[需测：xxx]` 的对象）：

- 文字输入：违禁词命中预期文案 / 谐音字变体（"草尼玛"等） / Unicode 替换字符 / HTML 标签 `<script>` `<img onerror>` / Markdown 图床注入 `![](evil.com)` / 超长换行符
- 图片上传：色情/暴恐/政治图测试样本（用脱敏占位数据） / 含 EXIF 隐私信息（GPS/设备） / 伪装为 jpg 的脚本文件 / SVG 含 `<script>`
- 视频上传：违规音频片段 / 违规画面截帧
- URL 输入：钓鱼站短链 / IDN 同形异义攻击域名 / data: 伪协议

**输出要求**：

- 按"测试对象"分组
- 格式：`编号 / 维度 / 测试点（含具体数据） / 关注的 Bug / 优先级`
- 测试点必须是具体可执行值，不写抽象项
- 同一对象至少覆盖 3 个维度；核心对象至少 6 个维度

## 步骤 3：用例细化

把步骤 2 的测试点扩写为标准测试用例，**统一以 markdown 表格输出**，按「所属模块（功能 X）」分组，每组一张表。

**表格列（固定 8 列，不增不减）**：

```
| 用例编号 | 所属模块 | 优先级 | 用例标题 | 前置条件 | 测试数据 | 测试步骤 | 预期结果 |
```

**列约束**：

| 列名 | 约束 |
|------|------|
| 用例编号 | 格式 `TC_{模块缩写}_{3位序号}`，如 `TC_RDM_001`、`TC_LOGIN_012` |
| 所属模块 | 直接写步骤 1a 定义的「功能 X」（如 `功能 1：兑换成功流程`） |
| 优先级 | P0 / P1 / P2 |
| 用例标题 | 动宾结构 ≤ 15 字（如「11 位非 1 开头号码触发校验」） |
| 前置条件 | **必须是 QA 可执行步骤**（编号 1. 2. 3.，用 `<br>` 串联）。涉及业务实体（订单/用户/SKU）必须说明"通过 xxx 入口创建/Mock，参数 yyy"，并给该实体命名（`orderA` / `userA`）。**禁用伪代码**："服务端当前-1s" → 改为"通过测试后台 Mock 接口把 completedAt 设为'测试执行时刻 - 1 秒'" |
| 测试数据 | 分两类：<br>① **原子数据**（字符串/数字/emoji/边界值）必须给具体值——禁用"超长字符串"，写"1001 个汉字"；禁用"D-30 天"，写绝对时间或可执行表达式<br>② **业务实体**禁用 O1/U1/S1 等占位符代号，改用前置条件中**已命名**的实体引用（如 `orderA`）<br>多值用 `;` 分隔 |
| 测试步骤 | 单格内 `1. xxx <br> 2. xxx`；动词开头（输入/点击/等待/切换/滑动）；禁用"测试 xxx"。步骤中的业务实体必须从前置条件/测试数据可追溯（不能突然出现 O1）；**非测试动作**（改服务端时间/设备时区/系统日期）必须明确依赖：写"通过测试后台 Mock 接口..." 或 "通过开发者菜单 → 设置 → ..."，禁用"飞至 UTC-5"这种 |
| 预期结果 | 单格内 `1. xxx <br> 2. xxx`，编号对应步骤；必须可验证（含文字、位置、状态）；禁用"正常显示"；涉及异步明确等待时长（"≤ 2s"） |

**完整正例**（一条用例覆盖 3 个难点：业务实体 + 相对时间 + 平台配置）：

| 用例编号 | 所属模块 | 优先级 | 用例标题 | 前置条件 | 测试数据 | 测试步骤 | 预期结果 |
|---|---|---|---|---|---|---|---|
| TC_ENT_001 | 功能 1：评价入口 | P0 | 刚完成订单可立即评价 | 1. 用 testuser_qa01 登录 App<br>2. 通过测试后台 Mock 接口创建订单 orderA：商品='测试商品 A'，status='已完成'，completedAt='测试执行时刻 - 1 秒' | 订单 orderA（由前置条件创建） | 1. 进入「我的订单 → 已完成」Tab<br>2. 点击 orderA 行的「评价」按钮 | 1. 跳转到评价页 ≤ 2s<br>2. 页面顶部展示 orderA 商品图与名称，5 颗星均未选中，文字输入框为空 |

**分组规则**：

- 每个「功能 X」一张独立表格，表格上方加 `### 功能 X：xxx` 二级标题
- 同一测试点 → 一条用例；数据不同需拆分时除外

**输出末尾必须追加导出说明**：

```
以上表格可直接复制粘贴到 Excel / 飞书多维表格 / Numbers，自动转表。
  • 测试步骤 / 预期结果中的 <br> 在 Excel 中显示为换行（粘贴时若未自动识别，按 Ctrl+H 替换 <br> 为 Alt+Enter）
  • 飞书多维表格 / Notion 可直接识别
```

然后接通用暂停确认块（步骤 3 用常规规则）。

## 步骤 4：反向挑刺

切换为【对抗性 QA Lead】视角，审查步骤 3 用例集。**直接挑毛病，不客气，不拍马屁**。

**输出 5 部分**：

1. 【遗漏】至少挑 5 条漏掉的测试点，按维度分类，每条说明"为什么重要 + 真实可能的 bug"
2. 【冗余】重复或可合并的用例（用例编号 + 合并建议）
3. 【不可执行】步骤模糊 / 数据不具体 / 预期不可验证的用例（用例编号 + 具体问题）
4. 【优先级偏差】P0/P1/P2 标错的用例（用例编号 + 调整建议 + 理由）
5. 【致命盲点】回答：
   "如果这个产品上线后出 P0 故障，最可能是什么场景？这套用例集能发现它吗？"
   不能就明说不能，给出补救用例。

**风格**：

- 用具体例子，不要泛泛"建议加强测试"
- 不要客气，不要给"整体不错，但是..."的开头
- 真挑不出问题就直接说"无明显遗漏"，不许凑数

**步骤 4 特殊暂停规则**：

```
已完成 [步骤 4：反向挑刺]

回复「全部采纳」/ 「采纳 1、3、5」/ 「全部拒绝」/ 「针对 X 条再讨论」。
合并完成后再次暂停。
```

---

## 步骤 5：覆盖度自评

基于步骤 1a 的需求拆解 + 步骤 4 修正后的最终用例集，输出**交付清单**（给 PM / Dev / 老板评审用）。

**▼ 1. 功能覆盖矩阵（markdown 表格）**

| 功能编号 | 功能名称 | 覆盖用例编号 | 用例数 |
|------|------|------|------|
| 功能 1 | xxx | TC_RDM_001, TC_RDM_002, ... | N |
| 功能 2 | xxx | TC_RDM_010, ... | M |

**▼ 2. 缺口分析（必须具体，禁止泛泛"测试不足"）**

- 哪些功能覆盖不足 → 写出具体功能编号 + 缺什么（如「功能 3 缺并发兑换场景」）
- 哪些维度明显薄弱 → 写出具体维度 + 影响（如「时序维度仅 2 条，可能漏掉超时类 bug」）
- 哪些方法没用上 → 说明是不适用还是漏了

**▼ 3. 主动放弃声明**

格式：`[场景] | [放弃原因] | [遗留风险]`

示例：
- `iOS 13 以下机型兼容性 | 用户量 < 0.5% 性价比低 | 老机型用户可能无法兑换`
- `压测 1 万并发 | 当前阶段不需要 | 大促前需补测`

**▼ 最后一行**

> "这套用例集能发现 ___ 类 bug，发现不了 ___ 类 bug"

**收尾提醒**（不再追加暂停块）：

```
全流程已结束。最终用例表（步骤 3 + 步骤 4 修正版）和覆盖矩阵均可直接粘贴到 Excel / 飞书多维表格。
```

## 反模式提醒

- ❌ 一次性跑完所有步骤不暂停
- ❌ 步骤 1a 跳过歧义清单直接给"完美需求"
- ❌ 步骤 1a 把需求原文按句拆条当作"显式功能点"（如"F1 输入兑换码 / F2 弹 toast / F3 列表新增"）
- ❌ 步骤 1a 一条歧义里塞多个产品决策
- ❌ 步骤 1a 把"可能方向"当作默认假设让用户一键采纳；用户没回答就替他选 A
- ❌ 步骤 1b 用户回复"待 PM 确认"时 skill 自行决策填值（应在规格中显式标注"待 PM 确认"）
- ❌ 测试对象含文字/图片/视频/URL 输入但跳过内容安全（敏感词、敏感图、富文本注入、恶意链接）
- ❌ 业务实体（订单/用户/SKU）用 O1/U1/S1 等抽象占位符代号代替真实数据
