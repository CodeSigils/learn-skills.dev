Erkennen Sie Code-Gerüche und wenden Sie *direkte* Refactoring-Techniken an (Methode/Klasse extrahieren, Bedingung ersetzen, Parameterobjekt einführen, Umbenennen, Verschieben), um die Klarheit, Testbarkeit und Wartbarkeit einer einzelnen Funktion, Klasse oder Datei zu verbessern.
TRIGGER, wenn: Benutzer Refactoring-Möglichkeiten, Code-Geruch, lange Methode, große Klasse, primitive Besessenheit, lange Parameterliste, Datenklumpen, Feature-Neid, Shotgun-Operation, Switch-Anweisungs-Geruch, Methode extrahieren, Klasse extrahieren, Bedingung durch Polymorphismus ersetzen, Parameterobjekt einführen, einzelne Datei vereinfachen, Lesbarkeit verbessern, aufräumen, zuerst aufräumen, „diese Funktion bereinigen“, „diese Klasse umgestalten“.
NICHT VERWENDEN, wenn: keine Tests vorhanden sind (unsicher für blindes Refactoring – fügen Sie zuerst Tests hinzu), die Änderung verhaltensverändernd und nicht nur strukturell ist (verwenden Sie stattdessen „tcrdd“) oder der Benutzer ein *dateiübergreifendes* Abhängigkeitsdiagramm sicher entwirren muss, in dem sich eine Änderung auf viele Aufrufseiten auswirkt (verwenden Sie stattdessen „mikado-method“).
