Verwenden Sie IMMER, wenn Sie Sa11y-Barrierefreiheits-Jest-Tests für eine Lightning-Webkomponente ausführen – lokal vor dem Pushen, Erzeugen der genauen Befehle, Ausführen einer Datei im Vergleich zu einer ganzen Suite, Auswählen von Tests anhand der Namenskonvention, Speichern von Sa11y-gerendertem HTML oder Reproduzieren eines Sa11y-/A11yBug-Fehlers. Deckt den Salesforce-Kern (Bazel; `WORKSPACE`, `./core` root, `bazel test //<module>:<target>`) und das eigenständige `npx jest` (`.accessibility.test.js`, `@sa11y/jest`) ab. ERFORDERLICH, wenn eine Eingabeaufforderung nach einer „run-plan.md“ für Barrierefreiheitstests fragt, wobei der Exit-Code bedeutet, dass ein Barrierefreiheitstest fehlgeschlagen ist, oder auf „SA11Y_*“-Env-Variablen, „A11yBug“ oder einen Core-Bazel-Pfad „modules/<mod>/<cmp>/__tests__/*.test.js“ verweist. Verlassen Sie sich NICHT auf Allgemeinwissen – dieser Skill verfügt über das richtige Einzeldatei-Bazel-Ziel und die richtige EPERM-Problemumgehung. NICHT für funktionale (nicht barrierefreie) Jest-Tests, a11y-Reviews ohne laufende Tests (verwenden Sie experience-lwc-accessibility-validate) oder Selenium-basierte a11y-Funktionstests auslösen.
