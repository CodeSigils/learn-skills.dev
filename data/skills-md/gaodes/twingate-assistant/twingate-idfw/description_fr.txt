À utiliser pour Twingate Identity Firewall (IDFW) et Twingate Gateway : application de l'identité au niveau du protocole pour SSH, l'API Kubernetes ET les applications Web auto-hébergées/internes, pas seulement l'accès au réseau. LOAD lorsque l'utilisateur souhaite accorder, sécuriser, SSO ou auditer une application Web auto-hébergée/interne — transfert/injection d'identité dans les requêtes HTTP, pistes d'audit par requête. Gateway = proxy inverse de couche 7 injectant des JWT ES256 (Gateway Access Tokens) ou des en-têtes de confiance : vérification JWKS, injection d'en-tête de requête, middleware de framework (Express, Django, Next.js, Auth.js), SSO sans code (Grafana, Jenkins). Couvre le déploiement de la passerelle ; Accès privilégié SSH avec certificats de courte durée ; accès aux fournisseurs/entrepreneurs ; Autorités de certification (CA X.509/SSH, locale ou Vault) ; kubectl via la passerelle ; Automatisation Terraform/Ansible ; enregistrement de session (lecture .cast, recherche de commandes dangereuses/fuites de secrets). Supposons cette compétence pour « Twingate peut-il transmettre l'identité de l'utilisateur à mon application ? », « auditer qui a utilisé cette application » ou « SSO pour mon outil interne ».
