Développement axé sur les preuves : entourez la mise en œuvre d'une spécification exécutable et d'un ensemble de contraintes (tests, types, couverture, mutation), afin que l'examen ligne par ligne devienne facultatif. À utiliser lorsque l'utilisateur demande explicitement un travail de haute assurance ou axé sur les preuves (« fiable », « TDD », « prouver que cela fonctionne », « Je ne lirai pas le code »), ou lorsque le changement touche des domaines à enjeux élevés (argent, authentification, perte de données, concurrence, API publique). Pour les changements de routine où l'utilisateur souhaite simplement des tests normaux, écrivez directement de bons tests au lieu d'invoquer cette boucle.
