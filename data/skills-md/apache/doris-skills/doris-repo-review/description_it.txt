Data un URL di PR (`/doris-repo-review https://github.com/apache/doris/pull/66807`), controlla innanzitutto se il branch e il commit della directory corrente corrispondono a quella PR; se non corrispondono, allinea la directory corrente alla testa della PR senza disturbare il lavoro locale (rifiuta lo switch quando i file tracciati sono modificati e restituisci la decisione all'utente). Successivamente esegui la revisione usando la stessa pipeline che il CI di apache/doris utilizza (Code Review Runner): scansione di rischi con l'agent principale, da 1 a 3 sub‑agent di revisione completa più sub‑agent focalizzati sul rischio, convergenza del shared‑ledger (massimo 3 round) e genera un documento di revisione in inglese e uno in cinese nella cartella `review-docs/`. Un'esecuzione locale non produce commenti inline su GitHub, quindi ogni riscontro deve includere un ancoraggio `percorso:linea` e uno snippet verbatim, verificato da uno script. Quando la revisione supera i controlli (nessun Blocker e nessun Major), pubblica un unico commento PASS, fortemente formattato e leggibile da macchine, sul PR usando l'account locale di gh—incluse data di revisione, SHA del commit revisionato, stato, modello e note per i maintainer—mostrando prima il corpo esatto all'utente per conferma. Usa questa logica quando l'utente digita “/doris-repo-review <PR URL>”, “review this PR”, “review it the way the CI pipeline does” o “review this PR locally like CI”. Operazione in sola lettura sul sorgente: nessuna compilazione, nessun test, nessuna modifica ai file del repository; il commento PASS è l'unica scrittura su GitHub, mentre una revisione REQUEST_CHANGES non pubblica nulla.  

Rispondi sempre nella lingua dell'utente.
