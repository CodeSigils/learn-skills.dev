HTTP リクエストの密輸を追跡します (CL.TE、TE.CL、H2.CL、H2.TE)。原因: フロントエンド プロキシとバックエンド サーバーは、1 つのリクエストがどこで終了し、次のリクエストが始まるかについて意見が一致していません (Content-Length と Transfer-Encoding ヘッダーの解析の不一致)。 CL.TE: フロントエンドは CL を使用し、バックは TE を使用します。→ TE を送信することで密輸します。チャンク化されていますが、CL 数に適合するボディを使用します。 TE.CL：反対です。 H2.CL: HTTP/2 ダウングレード、CL を HTTP/1.1 バックエンドに密かに取り込みます。検出ツール: Burp HTTP Request Smuggler 拡張機能、smuggler.py、h2csmuggler。確認: 時間遅延テクニック (30 秒のタイムアウトで密輸された GET) — 次の被害者のリクエストでフロントエンドが応答が遅い場合、密輸は機能します。検証: キャッシュ ポイズニング チェーン (被害者のためにキャッシュされる密輸リクエスト)、資格情報の盗難 (次のユーザーの Cookie をキャプチャする X-Forwarded-For オーバーライドの密輸)、認証バイパス (密輸された内部パス リクエスト)。主要な CDN 導入からの実際の有料サンプル。 CDN+オリジンスタックを実行しているH1有料プログラムを探す場合、ロードバランサー/WAFバイパスをターゲットにする場合に使用します。
