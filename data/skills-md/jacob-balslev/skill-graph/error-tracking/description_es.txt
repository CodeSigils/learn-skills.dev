Úselo al diseñar o ampliar la canalización de informes de excepciones para una aplicación: elegir dónde se encuentran los límites de error (componente, sección, ruta, aplicación global), empaquetar el SDK del rastreador para que cada llamada de informes esté desinfectada y controlada por el entorno, adjuntando el contexto del usuario sin filtrar PII y verificando que los errores de cada capa realmente lleguen al rastreador. Cubre el modelo de captura de errores de cuatro superficies (límites de componentes, rutas alternativas, controlador de fallas globales, API manual), diseño de contenedor centralizado (`reportError` / `reportMessage` / `addBreadcrumb` / `setUser`), desinfección de PII antes de cualquier envío externo, puerta consciente del entorno (dev → registrador local, prod → tracker SDK) y la pregunta de diagnóstico: "¿Esta capa realmente informa, o solo lo hace?" ¿registro?' NO lo use para el error *visual* UX visto por el usuario (use `a11y` para mensajes de error accesibles y flujos de recuperación), para buscar un único error observado ya capturado en el rastreador (use `depuración`) o para la política más amplia de privacidad y retención de PII (use `owasp-security`).
