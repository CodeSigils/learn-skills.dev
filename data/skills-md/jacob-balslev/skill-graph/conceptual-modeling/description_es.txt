Úselo al traducir los requisitos comerciales en una representación de dominio estructurada, diseñar una nueva característica desde cero o validar que la estructura de un sistema coincida con la realidad comercial, antes de nombrar cualquier esquema de base de datos, punto final de API o límite agregado. Cubre la identificación de entidad/atributo/relación, cardinalidad (1:1, 1:N, M:N, 0..1, 1..*), generalización versus especialización (desjunta/superpuesta, total/parcial), agregación versus composición, modelado de roles, la escalera de abstracción conceptual → lógica → física, validación contra los modelos mentales de las partes interesadas del negocio y los siete antipatrones (fuga de implementación, entidad faltante, entidad divina, relación fantasma, normalización prematura, atributo-como-entidad, relación sin nombre). NO lo use para diagramas ER específicos de bases de datos con PK / FK / normalización (use una habilidad de modelado lógico), axiomas de ontología formales con OWL o RDFS (use una habilidad de ontología) o diseño táctico DDD (agregados, contextos acotados): el modelado conceptual permanece en una capa por encima de los tres.
