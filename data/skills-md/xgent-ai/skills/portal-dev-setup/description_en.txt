In your own app’s repository, use Docker to spin up a real XGENT.ai portal (a one‑box) for local integration testing—without cloning the portal, without modifying portal code, and without rebuilding the portal image. A single `onebox.sh init` checks the local puller credentials (`REGISTRY` + `PULLER_AUTH` in `.xgent‑registry.env`; if they’re missing, it stops and asks the user to get them from the development team) → automatically performs `docker login` and pulls the portal image → extracts the compose assets from the image, selects free ports, generates `compose.env`; then follows a fixed order: `migrate` → `seed` → `register‑app` → bring up the stack, after which an iframe/curl can run the full end‑to‑end flow. For any task that involves “connecting my app to the portal for the first time / launching a one‑box / running a local portal / pulling the portal image / failing local portal integration / resetting a one‑box”, or when you encounter errors such as failing to pull the portal image, `unauthorized`, `denied`, `/svc/<key>` 404 or 502, localhost unreachable, `port is already allocated`, `COMPOSE_PROJECT_NAME` collision that takes over other containers, `portal‑api` constantly unhealthy, `register‑app` reporting `VALIDATION_FAILED`, self‑inspection 401, a valid TDT judged `INVALID_TOKEN`, iframe blank screen, cross‑app exchange getting 401 on the initiator, etc., be sure to first use this skill before running `docker compose`—even if the user only says “bring the portal up”. Use when an external App team brings up, smoke‑tests, resets, or debugs a real XGENT portal locally (the one‑box Docker stack) from their own repo, without the portal monorepo.
