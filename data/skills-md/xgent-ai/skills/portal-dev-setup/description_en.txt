In your own app’s repo, use Docker to spin up a real XGENT.ai portal (a one‑box) for local integration testing—without cloning the portal, without modifying portal code, and without rebuilding the portal image. A single `onebox.sh init` checks local puller credentials (the `REGISTRY` and `PULLER_AUTH` in `.xgent-registry.env`; if missing, halt and have the user obtain them from the development team) → automatically `docker login` and pull the portal image → extract the compose assets from the image, pick free ports, generate `compose.env`; then, in a fixed order, run `migrate` → `seed` → `register-app` → start the stack, and finally use iframe/curl to verify the full chain.  

For any task that involves “first time connecting my app to the portal for debugging / spin up a one‑box / start a local portal / pull the portal image / local portal integration failing / one‑box reset”, or when errors such as failure to pull the portal image, unauthorized, denied, `/svc/<key>` 404 or 502, localhost unreachable, “port is already allocated”, `COMPOSE_PROJECT_NAME` collision causing other containers to be taken over, portal‑api constantly unhealthy, `register‑app` reporting `VALIDATION_FAILED`, introspection 401, a valid TDT being judged `INVALID_TOKEN`, iframe white screen, cross‑application exchange getting 401 on the initiator, etc., be sure to first use this skill before running `docker compose`—even if the user only says “bring the portal up”.  

Use when an external app team brings up, smoke‑tests, resets, or debugs a real XGENT portal locally (the one‑box Docker stack) from their own repo, without the portal monorepo.
