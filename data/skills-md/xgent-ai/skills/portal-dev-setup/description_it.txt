Nel repository della tua app, utilizza Docker per creare un vero portale XGENT.ai (un one-box) per i test di integrazione locale, senza clonare il portale, senza modificare il codice del portale e senza ricostruire l'immagine del portale. Un singolo `onebox.sh init` controlla le credenziali del puller locale (`REGISTRY` e `PULLER_AUTH` in `.xgent-registry.env`; se mancanti, arresta e chiedi all'utente di ottenerle dal team di sviluppo) → automaticamente `docker login` ed estrai l'immagine del portale → estrai le risorse di composizione dall'immagine, seleziona le porte libere, genera `compose.env`; quindi, in un ordine fisso, esegui `migrate` → `seed` → `register-app` → avvia lo stack e infine utilizza iframe/curl per verificare l'intera catena.  

Per qualsiasi attività che implica "la prima connessione della mia app al portale per il debug / avvio di un one-box / avvio di un portale locale / pull dell'immagine del portale / integrazione del portale locale non riuscita / ripristino di un one-box" o quando errori come errore nel pull dell'immagine del portale, non autorizzato, negato, `/svc/<key>` 404 o 502, localhost non raggiungibile, "porta già allocata", collisione `COMPOSE_PROJECT_NAME` che causa il controllo di altri contenitori, portale‑api costantemente non integro, `register‑app` che riporta `VALIDATION_FAILED`, introspezione 401, un TDT valido giudicato `INVALID_TOKEN`, schermo bianco iframe, scambio tra applicazioni che ottiene 401 sull'iniziatore, ecc., assicurati di utilizzare questa abilità prima di eseguire `docker compose`, anche se l'utente dice solo "avvia il portale".  

Da utilizzare quando un team di app esterno attiva, effettua test di fumo, reimposta o esegue il debug di un vero portale XGENT localmente (lo stack Docker a una casella) dal proprio repository, senza il monorepo del portale.
