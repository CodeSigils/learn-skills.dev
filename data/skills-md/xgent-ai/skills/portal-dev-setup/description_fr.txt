Dans le référentiel de votre propre application, utilisez Docker pour créer un véritable portail XGENT.ai (une boîte unique) pour les tests d'intégration locale, sans cloner le portail, sans modifier le code du portail et sans reconstruire l'image du portail. Un seul `onebox.sh init` vérifie les informations d'identification de l'extracteur local (le `REGISTRY` et `PULLER_AUTH` dans `.xgent-registry.env` ; s'il est manquant, arrêtez-le et demandez à l'utilisateur de les obtenir auprès de l'équipe de développement) → automatiquement `docker login` et extrayez l'image du portail → extrayez les actifs de composition de l'image, choisissez les ports libres, générez `compose.env` ; puis, dans un ordre fixe, exécutez `migrate` → `seed` → `register-app` → démarrez la pile, et enfin utilisez iframe/curl pour vérifier la chaîne complète.  

Pour toute tâche impliquant « la première connexion de mon application au portail pour le débogage / la mise en route d'un one-box / le démarrage d'un portail local / l'extraction de l'image du portail / l'échec de l'intégration du portail local / la réinitialisation d'un one-box », ou lorsque des erreurs telles que l'échec de l'extraction de l'image du portail, non autorisé, refusé, `/svc/<key>` 404 ou 502, localhost inaccessible, "le port est déjà alloué", une collision `COMPOSE_PROJECT_NAME` provoquant la prise d'autres conteneurs terminé, l'API du portail est constamment en mauvais état, `register-app` signalant `VALIDATION_FAILED`, introspection 401, un TDT valide jugé `INVALID_TOKEN`, écran blanc iframe, échange inter-applications obtenant 401 sur l'initiateur, etc., assurez-vous d'utiliser d'abord cette compétence avant d'exécuter `docker compose` - même si l'utilisateur dit seulement « ouvrir le portail ».  

À utiliser lorsqu'une équipe d'application externe crée, teste, réinitialise ou débogue localement un véritable portail XGENT (la pile Docker à boîte unique) à partir de son propre référentiel, sans le monorepo du portail.
