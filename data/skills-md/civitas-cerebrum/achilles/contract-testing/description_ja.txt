バックエンド HTTP エンドポイントがテスト (書き込み、実行、レビュー、または呼び出し) で使用されるときは常に使用します。スキルは、ステータス コードの期待値、応答スキーマ アサーション、エラー エンベロープ検証、ヘッダー カバレッジなど、API インタラクションごとに生成される構造化された形状を所有します。これは、明示的意図のトリガー (契約テスト、スキーマ テスト、協定、OpenAPI 準拠、API 契約のロック、API 形状の検証、重大な変更の検出、消費者主導の契約、プロバイダーの検証、API 互換性、仕様準拠、API が変更されていないことの確認) および「steps.apiGet」、「steps.apiPost」、「steps.apiPut」を呼び出す任意のテストまたは計画されたテストで自動的にアクティブ化されます。 `steps.apiDelete`、`steps.apiPatch`、`steps.apiHead`、`steps.verifyApiStatus`、または `steps.verifyApiHeader` — UI フロー仕様内であっても。理論的根拠: すべてのバックエンド呼び出しには、少なくともステータス コード + エラー エンベロープ アサーションが必要です。これらがないと、エンドポイントがリグレッションすると、テストは静かにパスします。また、バックエンド インタラクションが到着しようとしていることを示すフレーズ (「テストで API を呼び出す」、「バックエンドに対してテストする」、「API を使用する」、「応答を検証する」、「JSON 形状をアサートする」、「API 応答を検証する」、「バックエンドの応答をロックする」、「エンドポイントが返す必要がある」、および仕様コンテキスト内のプロジェクト URL に対する HTTP 動詞の言及でもアクティブになります。実際のルート: 要素インタラクションのコンパニオン スキル テーブル (ここでコントラクト インテントをルーティングします)、直接ユーザー インテント、およびテストコンポーザーのステップ 3 実装ルール。バリアントがコントラクト シェイプをオプションとして扱うのではなく、バリアントが `steps.api*` 行を発行するたびにスキル ツール経由でこのスキルを呼び出します。対象外: 純粋な UI フロー アサーション、ジャーニー スコープでの対象範囲の拡大、ページ レベルでのバグ探索、または不合格テストの診断 — これらは独自のスキルに帰されます。
