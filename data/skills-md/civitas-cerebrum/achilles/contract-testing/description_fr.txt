À utiliser chaque fois qu'un point de terminaison HTTP backend est utilisé dans un test : écriture, exécution, révision ou simplement appel. La compétence possède la forme structurée que chaque interaction API devrait produire : attentes en matière de code d'état, assertion de schéma de réponse, validation d'enveloppe d'erreur, couverture d'en-tête. Il s'active auto- `steps.apiDelete`, `steps.apiPatch`, `steps.apiHead`, `steps.verifyApiStatus` ou `steps.verifyApiHeader` — même à l'intérieur d'une spécification de flux d'interface utilisateur. La justification : chaque appel backend mérite au minimum une assertion de code d'état + d'enveloppe d'erreur ; sans ceux-ci, le test réussit silencieusement lorsque le point final régresse. S'active également sur les phrases qui signalent qu'une interaction backend est sur le point d'atterrir : "appeler l'API dans un test", "tester sur le backend", "consommer l'API", "vérifier la réponse", "affirmer la forme JSON", "valider la réponse de l'API", "verrouiller la réponse du backend", "le point de terminaison doit revenir" et toute mention d'un verbe HTTP par rapport à une URL de projet dans un contexte de spécification. Itinéraires réels dans : la table des compétences associées aux interactions entre éléments (qui achemine ici l'intention du contrat), l'intention directe de l'utilisateur et la règle d'implémentation Étape 3 du compositeur de test, qui appelle cette compétence via l'outil Compétence chaque fois qu'une variante émet des lignes `steps.api*` plutôt que de traiter la forme du contrat comme facultative. Pas pour : les assertions de flux d'interface utilisateur pures, l'expansion de la couverture au niveau du parcours, la recherche de bogues au niveau de la page ou le diagnostic d'échec des tests – ceux qui mènent à leurs propres compétences.
