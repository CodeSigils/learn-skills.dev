Da utilizzare per Twingate Identity Firewall (IDFW) e Twingate Gateway: applicazione dell'identità a livello di protocollo per SSH, API Kubernetes e app Web self-hosted/interne, non solo per l'accesso a livello di rete. LOAD ogni volta che l'utente desidera concedere, proteggere, eseguire SSO o controllare l'accesso a un'applicazione Web interna o self-hosted, incluso l'inoltro o l'inserimento dell'identità dell'utente che ha effettuato l'accesso nelle richieste HTTP o un audit trail per utente/a livello di richiesta di chi ha effettuato l'accesso a un'app. Questo è il gateway che agisce come proxy inverso di livello 7 che inserisce JWT ES256 (Gateway Access Tokens) firmati o intestazioni attendibili nelle app Web: verifica JWKS, iniezione di intestazioni di richiesta, middleware del framework (Express, Django, Next.js, Auth.js) e integrazioni SSO senza codice (Grafana, Jenkins). Da utilizzare anche quando l'utente distribuisce il Gateway; configura l'accesso privilegiato SSH con certificati di breve durata; gestisce l'accesso privilegiato/fornitore/appaltatore; configura le autorità di certificazione (X.509 o SSH CA, locale o HashiCorp Vault); instrada kubectl attraverso il Gateway; automatizza IDFW con Terraform o Ansible; o implementa/revisiona la registrazione della sessione (riproduzione e archiviazione di asciicast/.cast, scansione di sessioni SSH o kubectl registrate per comandi pericolosi o segreti trapelati, hosting autonomo di un'interfaccia utente di navigazione per la registrazione). Se una domanda riguarda l'accesso in base all'identità a un'app o a un host ("Twingate può trasferire l'identità dell'utente alla mia app?", "controlla chi ha utilizzato questa app", "SSO per il mio strumento interno") - presumi che questa competenza sia pertinente e caricala.
