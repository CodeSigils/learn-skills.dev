À utiliser pour Twingate Identity Firewall (IDFW) et Twingate Gateway : application de l'identité au niveau du protocole pour SSH, l'API Kubernetes ET les applications Web auto-hébergées/internes, et pas seulement l'accès au niveau du réseau. LOAD chaque fois que l'utilisateur souhaite accorder, sécuriser, SSO ou auditer l'accès à une application Web auto-hébergée ou interne - y compris le transfert ou l'injection de l'identité de l'utilisateur connecté dans les requêtes HTTP, ou une piste d'audit par utilisateur/au niveau de la requête indiquant qui a accédé à une application. Il s'agit de la passerelle agissant comme un proxy inverse de couche 7 qui injecte des JWT ES256 signés (jetons d'accès de passerelle) ou des en-têtes de confiance dans les applications Web : vérification JWKS, injection d'en-tête de requête, middleware de framework (Express, Django, Next.js, Auth.js) et intégrations SSO sans code (Grafana, Jenkins). À utiliser également lorsque l'utilisateur déploie la passerelle ; configure l'accès privilégié SSH avec des certificats de courte durée ; gère les accès privilégiés/fournisseurs/entrepreneurs ; configure les autorités de certification (X.509 ou SSH CA, local ou HashiCorp Vault) ; achemine kubectl via la passerelle ; automatise IDFW avec Terraform ou Ansible ; ou implémente/examine l'enregistrement de session (lecture et archivage asciicast/.cast, analyse des sessions SSH ou kubectl enregistrées à la recherche de commandes dangereuses ou de secrets divulgués, auto-hébergement d'une interface utilisateur de navigation d'enregistrement). Si une question concerne l'accès conscient de l'identité à une application ou à un hôte — « Twingate peut-il transmettre l'identité de l'utilisateur à mon application ? », « auditer qui a utilisé cette application », « SSO pour mon outil interne » — supposez que cette compétence est pertinente et chargez-la.
