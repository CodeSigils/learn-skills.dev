سير عمل تطوير منضبط يعتمد على المواصفات ويعتمد على الاختبار لبناء البرامج باستخدام وكلاء ترميز الذكاء الاصطناعي. يحول الطلبات الغامضة إلى تطبيقات تم التحقق منها من خلال المواصفات المنظمة واشتقاق الاختبار وTDD الصارم. يتعامل مع المشاريع الجديدة، والتحسينات الأساسية (مع أو بدون الاختبارات الحالية)، وإعادة البناء، وإصلاحات الأخطاء المعقدة مع إرشادات خاصة بسير العمل لكل منها. يُستخدم عندما يطلب المستخدم ميزة جديدة، أو وحدة نمطية، أو تحسينًا، أو إعادة بناء، أو واجهة برمجة التطبيقات (API)، أو خط أنابيب البيانات، أو أداة واجهة سطر الأوامر (CLI)، أو نظامًا بمتطلبات متعددة، أو حالات حافة، أو مواصفات غير واضحة. استخدم أيضًا لإصلاحات الأخطاء المعقدة التي تتطلب تحليل السبب الجذري. تشغيل عبارات مثل "إضافة ميزة"، أو "تنفيذ"، أو "إنشاء وحدة نمطية جديدة"، أو "إنشاء واجهة برمجة تطبيقات"، أو "إنشاء واجهة سطر الأوامر"، أو "إنشاء خط أنابيب بيانات"، أو "إعادة البناء"، أو "إصلاح هذا الخطأ"، أو "كتابة اختبارات لـ"، أو "TDD"، أو "الاختبار أولاً"، أو "المتطلبات غير واضحة"، أو "اختبارات التوصيف"، أو "تحديد هذا الأمر". يتم تشغيلها عند تعديل التعليمات البرمجية باستخدام ملفات اختبار مجاورة (`tests/`، `*_test.py`، `*.test.ts`، `*.spec.ts`، `spec/`، `__tests__/`) أو تكوين إطار الاختبار (pytest.ini، jest.config.*، go.mod مع واردات الاختبار، Cargo.toml مع [تبعيات dev]، package.json مع برنامج نصي للاختبار). يتم تشغيله عندما يذكر المستخدم حالات الحافة، أو الثوابت، أو معايير القبول، أو تدوين EARS، أو إعادة البناء باللونين الأحمر والأخضر. لا تستخدم لإصلاحات سطر واحد بسيطة، أو تغييرات تجميلية، أو تنسيق، أو إعادة تسمية، أو مطبات التبعية، أو المهام حيث تم تحديد المتطلبات بالكامل بالفعل مع الاختبارات المقدمة.
