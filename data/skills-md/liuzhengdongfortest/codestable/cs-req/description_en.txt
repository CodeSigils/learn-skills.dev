Maintain requirement documents under `codestable/requirements/` for the project—describe existing capabilities using **user stories + plain language** covering "why it exists, how it solves the problem, and where the boundaries are," so non-technical readers can quickly grasp what makes the system stand out. Separate from architecture layers: requirement is the "problem space" (why this capability exists), architecture is the "solution space" (what structure implements it). **Requirements are status archives—only document capabilities that already exist with established boundaries, not "what we plan to do / what we'll add next"—those belong to cs-roadmap.** Primary path is feature-acceptance syncing back with code; this skill is the backup active entry point, with two modes: `update` (refresh existing docs based on new material or implementation changes, most common), `backfill` (create docs for capabilities that exist but never had documentation). Single-target rule—only modify one document at a time. Trigger scenarios: user says "refresh requirements directory," "this req doesn't match current code anymore," "this running capability never had a req, add one," or during feature-design phase when a capability to be implemented lacks a corresponding requirement. If user says "I want X capability" but X hasn't been built → don't use this skill, route to cs-roadmap instead.
