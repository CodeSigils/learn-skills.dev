Maintain the requirement documents under `codestable/requirements/` for the project—describe an already-existing capability in **user stories + plain language**, explaining “why it came to be, how it solves the problem, and where its boundaries lie,” so non-technical readers can grasp the system’s highlights at a glance. Keep it separate from architecture layers: requirements are the “problem space” (why this capability exists), architecture is the “solution space” (what structure implements it). **Requirements are a snapshot of the present—only capabilities that already exist with known boundaries; never “what we plan to do / will add next”—those belong to cs-roadmap**. The main path is feature-acceptance writing back in sync with code; this skill is a backup entry point with two modes: `update` (refresh existing doc with new facts or implementation changes, most common) and `backfill` (write a doc for a capability that’s live but never documented). One-doc rule—touch only one document per run. Triggered when users say “refresh the requirements folder,” “this req no longer matches the code,” “this running capability never got a req, add one,” or during feature-design when the capability to build has no linked requirement. If a user says “I want capability X” and X doesn’t exist yet → skip this skill, route to cs-roadmap.
