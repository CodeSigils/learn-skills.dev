Pflegen Sie Anforderungsdokumente unter „codestable/requirements/“ für das Projekt – beschreiben Sie vorhandene Funktionen mithilfe von **User Stories + einfacher Sprache** und behandeln Sie „warum es existiert, wie es das Problem löst und wo die Grenzen liegen“, damit auch technisch nicht versierte Leser schnell verstehen können, was das System auszeichnet. Getrennt von Architekturschichten: Anforderung ist der „Problemraum“ (warum diese Fähigkeit existiert), Architektur ist der „Lösungsraum“ (welche Struktur sie implementiert). **Anforderungen sind Statusarchive – nur Dokumentfunktionen, die bereits mit festgelegten Grenzen vorhanden sind, nicht „was wir vorhaben / was wir als Nächstes hinzufügen“ – diese gehören zur CS-Roadmap.** Primärer Pfad ist die Synchronisierung der Funktionsakzeptanz mit dem Code; Dieser Skill ist der aktive Backup-Einstiegspunkt mit zwei Modi: „Aktualisieren“ (Aktualisieren vorhandener Dokumente basierend auf neuem Material oder Implementierungsänderungen, am häufigsten), „Backfill“ (Erstellen von Dokumenten für Funktionen, die vorhanden sind, für die es aber noch nie eine Dokumentation gab). Einzelzielregel: Ändern Sie jeweils nur ein Dokument. Auslöseszenarien: Der Benutzer sagt „Anforderungsverzeichnis aktualisieren“, „Diese Anforderung stimmt nicht mehr mit dem aktuellen Code überein“, „Diese laufende Funktion hatte nie eine Anforderung, fügen Sie eine hinzu“ oder während der Feature-Design-Phase, wenn für eine zu implementierende Funktion eine entsprechende Anforderung fehlt. Wenn der Benutzer sagt „Ich möchte X-Fähigkeit“, aber X wurde noch nicht erstellt → Verwenden Sie diese Fähigkeit nicht, sondern leiten Sie sie stattdessen an cs-roadmap weiter.
