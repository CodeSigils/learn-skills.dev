Mantenga los documentos de requisitos en `codestable/requirements/` para el proyecto: describa las capacidades existentes usando **historias de usuarios + lenguaje sencillo** que abarque "por qué existe, cómo resuelve el problema y dónde están los límites", para que los lectores no técnicos puedan comprender rápidamente qué hace que el sistema se destaque. Separado de las capas de arquitectura: el requisito es el "espacio del problema" (por qué existe esta capacidad), la arquitectura es el "espacio de solución" (qué estructura la implementa). **Los requisitos son archivos de estado; solo documentan las capacidades que ya existen con límites establecidos, no "lo que planeamos hacer/lo que agregaremos a continuación", pertenecen a cs-roadmap.** La ruta principal es la sincronización de aceptación de características con el código; esta habilidad es el punto de entrada activo de respaldo, con dos modos: "actualizar" (actualizar documentos existentes según el nuevo material o cambios de implementación, el más común), "rellenar" (crear documentos para capacidades que existen pero que nunca tuvieron documentación). Regla de objetivo único: modifique solo un documento a la vez. Escenarios desencadenantes: el usuario dice "actualizar directorio de requisitos", "este requisito ya no coincide con el código actual", "esta capacidad en ejecución nunca tuvo un requisito, agregue uno" o durante la fase de diseño de características cuando una capacidad a implementar carece de un requisito correspondiente. Si el usuario dice "Quiero la capacidad X" pero X no se ha creado → no use esta habilidad, diríjase a cs-roadmap en su lugar.
