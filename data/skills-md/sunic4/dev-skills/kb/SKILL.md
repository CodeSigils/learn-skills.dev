# KB - 知识库

## 职责
**raw 接收（opt-in）→ 去重合并 → 质量检查 → 发布到正式目录 → 检索复用**

KB 是知识流的**唯一整理者**（curator）。其他技能只负责按需写 raw 和读正式目录。

**核心原则：质量 > 数量。不记一条无用的，也不漏掉一条确实有价值的。**

## 目录结构（两阶段）

```
wiki/knowledge/
├── raw/                        # ← 阶段1: 原始写入区
│   ├── {YYYYMMDD-HHMM}-{slug}.md   # 各技能写到这里
│   └── ⚠️ 此目录内容不可被其他技能检索
│
├── patterns/                   # ← 阶段2: 正式发布区 (可被读取)
│   └── {slug}.md              # status: verified
│
├── lessons/
│   └── {slug}.md
│
├── decisions/
│   └── {slug}.md
│
├── references/
│   └── {slug}.md
│
└── _archive/                  # ← 阶段3: 归档 (过时但保留)
    └── {YYYY-MM}-{slug}.md   # status: deprecated
```

**核心规则**:
- **raw/** = 写入目标，**不可被检索**
- **patterns/ lessons/ decisions/ references/** = 读取目标，**只有经过整理的条目才在这里**
- **_archive/** = 已废弃条目的归宿

## 触发方式

### 方式 A: 嵌入式触发 — 各技能写 raw（不经过 KB）

*(完整触发表见 `dev/SKILL.md` § KB嵌入式触发表 — 权威定义)*

各技能写入时直接写到 `wiki/knowledge/raw/`，不调用 KB 技能本身。

### 方式 B: 整理发布 — KB 技能自身执行

以下时机触发 KB 整理流程：
- 用户显式要求"整理知识库"/"review kb"
- `raw/` 中累积 ≥ 3 条未整理条目
- 其他技能检索时发现相关内容在 raw 中而非正式目录（提示用户整理）

### 方式 C: 显式调用（独立使用）
- 用户主动要求"记下来" → 直接写 raw → 可选立即整理
- 复盘/回顾时批量整理 raw → 正式目录
- 新成员 onboarding 时补充文档

## 整理流程（核心）

```
raw/ 中的条目
    │
    ▼
┌─────────────────────┐
│ Step 1: 去重扫描     │
│ (5维度，见下方)       │
└──────────┬──────────┘
           │
     ┌─────┴─────┐
     ↓           ↓
  精确匹配     非精确(语义重叠/跨分类/版本演化)
     │           │
     ↓           ↓
  更新旧条目   进入 Step 2 质量检查
     │
     ↓
┌─────────────────────┐
│ Step 2: 质量门槛     │
│ (5项检查)            │
└──────────┬──────────┘
           │
     ┌─────┴─────┐
     ↓           ↓
  全部通过      有缺陷
     │           │
     ↓           ↓
  发布到        保持 raw/ 或
  正式目录       补充后发布
                (标记需人工确认)
```

## Step 1: 去重逻辑（5 维度）

对每条 raw 条目，按以下顺序执行：

### 1.1 精确匹配（Exact Match）

```
Grep pattern: "{标题关键词}"
target: wiki/knowledge/{对应正式子目录}/*.md
```

| 结果 | 动作 |
|------|------|
| 标题相同 + 同一子目录 | **不创建新条目**。更新已有条目：追加 `updated` 时间戳 + 差异内容段落（标注来源日期） |
| 标题不同但正文 >80% 相同 | 同上，视为同一知识的变体 |

### 1.2 语义重叠（Semantic Overlap）

当 Grep 找到**部分匹配**（关键词重叠 40%-70%）时：

| 判断 | 动作 |
|------|------|
| 讲的是同一个问题的不同表现 | **合并**到更完整的那条，追加 `## 相关场景` 章节 |
| 讲的是不同问题但有共同根因 | 分别保留，互相添加 `see_also:` 链接 |
| 无法自动判断 | **保持 raw**，标注 `{待人工判断: 与 XXX 可能重复}` |

### 1.3 跨分类重复（Cross-Category）

检查**不同子目录之间**是否存在重复：

| 重复类型 | 示例 | 动作 |
|---------|------|------|
| lesson ≈ pattern | "不要在 useEffect 直接用 state"(lesson) vs "useEffect 依赖正确写法"(pattern) | **合并为一条 pattern**，在 pattern 中包含错误案例章节；删除 lesson 候选 |
| decision ≈ ADR | kb/raw/decision vs arch/decisions/ADR | **kb 条目只保留链接** `→ 详见 ADR-{NNN}`，不重复正文 |
| reference ≈ pattern | 速查代码片段 vs 完整模式描述 | reference **引用 pattern**，只保留速查部分 |

### 1.4 版本演化（Version Evolution）

| 场景 | 动作 |
|------|------|
| 新方案完全替代旧方案 | 旧条目移入 `_archive/`，旧条目标记 `superseded_by: ../{新slug}.md`；新条目写 `supersedes: ../_archive/{旧slug}.md` |
| 新方案是旧方案的补充/改进 | 在已有条目中追加 `## 更新 (YYYY-MM-DD)` 章节，保留历史 |
| 同一问题在不同上下文（技术栈/框架版本）| 两条都保留，互加 `see_also:` + 各自标注适用版本 |

### 1.5 自身去重（Raw 内部）

```
Grep pattern: "{关键词}"
target: wiki/knowledge/raw/*.md
```

如果 raw 内部已经有多条相似条目：
→ **先合并 raw 内部的**，再与正式目录做上述 1.1~1.4 判断

## Step 2: 质量门槛（Quality Gate）

每条知识进入正式目录前必须通过以下检查：

| # | 检查项 | 通过标准 | 不通过时的处理 |
|---|--------|---------|---------------|
| Q1 | **有明确标题** | 一眼知道讲什么 | 补充或生成标题 |
| Q2 | **有可运行代码示例** | 不是伪代码，可在项目中直接使用 | 补充真实代码；若为纯概念性内容则标注 `[概念]` |
| Q3 | **解释了"为什么"** | 不只是"怎么做"，包含原因分析 | 追加原因分析章节 |
| Q4 | **标注了适用场景和局限性** | 知道什么时候该用、什么时候不该用 | 补充局限说明 |
| Q5 | **不是纯链接/纯引用** | 正文有实质内容（≥ 3 行有效内容）| 如果只有链接 → 不创建独立条目，改为追加到目标条目的 `## 参考` 章节 |

**判定结果**:

| 结果 | 动作 | 目标位置 |
|------|------|---------|
| 5/5 通过 + 去重无冲突 | **自动发布** | 对应正式子目录 |
| 3-4 通过 + 有小缺陷 | **补充后发布**（Agent 自动补全）+ 标注 `{已自动补全}` | 对应正式子目录 |
| <3 通过 或 需要人工判断 | **保持 raw/** + 标注 `{待整理: 缺少 XXX}` | 留待下次整理 |

## 整理后的输出格式

正式目录中的每条知识必须包含：

```markdown
---
title: "{标题}"
category: pattern | lesson | decision | reference
source: "{来源技能} - {日期}"          # 如 "feat-impl - 2026-04-26"
see_also: []                            # 相关条目路径列表
supersedes: ""                          # 替代的旧条目路径（如有）
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
verified: true                          # 标识已通过质量检查
---

# {标题}

## 一句话总结
{用一句话说清楚这个知识点}

## 问题/场景
{什么情况下会遇到这个问题？}

## 解决方案
{具体做法 + 代码示例}

## 为什么这样做
{原因分析}

## 适用场景
- ✅ {适合的情况}
- ❌ {不适合的情况}

## 局限性 / 注意事项
{什么情况下这个方案不 work}
```

## 各类型的特殊要求

### Pattern（模式）
- 必须包含**完整的可复制代码**
- 注明**适用的技术栈/框架版本**
- 包含**至少一个反例**（错误做法对比）

### Lesson（教训）
- 必须**先写错误做法，再写正确做法**（对比结构）
- 包含**根本原因**(5 Whys 至少 2 层)
- 包含**预防措施**（如何避免再次踩坑）
- 命名: `{slug}.md`（不再带日期前缀，由 content 决定命名）

### Decision（决策）
- 如果已有 ADR → **只写一条引用条目**，正文只包含:
  ```markdown
  # {决策标题}
  
  > 此决策详见 [ADR-{NNN}](../../architecture/decisions/ADR-{NNN}.md)
  
  ## 快速结论
  {一句话结论}
  ```
- 如果没有对应 ADR → 按标准格式完整写

### Reference（参考）
- 允许**纯速查表格式**（不需要完整的为什么/局限性）
- 但必须有**使用场景说明**（一行即可）

## 维护规则

| 规则 | 说明 |
|------|------|
| 及时记录 | 解决问题后立即写 raw，不要依赖记忆 |
| 定期整理 | raw 累积 ≥ 3 条时触发整理，或用户主动要求 |
| 相互链接 | 整理时建立 see_also 关系 |
| 归档过时内容 | 被替代的条目移入 _archive/，不删除 |
| 单一事实源 | 同一知识点只在正式目录存一处 |

## 归档流程

### 归档触发条件（满足任一即触发）

| 条件 | 判断依据 |
|------|---------|
| 被新条目替代 | 去重 Step 1.4 判定为"完全替代"，新条目已发布到正式目录 |
| 技术栈/框架已废弃 | 条目标注的技术栈版本已 EOL ≥ 1 年（如 Node.js 12、AngularJS） |
| 长期无引用 | 正式目录中条目创建 ≥ 6 个月，且无其他条目 `see_also` 引用、无 raw 新增相关条目 |
| 用户显式要求 | "这个过时了"、"归档这条" |

### 归档操作流程

```
触发归档条件
     │
     ▼
┌─────────────────────┐
│ Step A1: 标记归档原因  │
│ (deprecated / superseded / eol / unused)       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Step A2: 更新 frontmatter │
│ status: deprecated                            │
│ superseded_by: "{新条目路径}" (如有)            │
│ archived_at: "YYYY-MM-DD"                     │
│ archive_reason: "{原因}"                       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Step A3: 移动到 _archive/ │
│ wiki/knowledge/{子目录}/{slug}.md              │
│   → wiki/knowledge/_archive/{YYYY-MM}-{slug}.md│
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Step A4: 更新引用链接    │
│ 检查所有正式目录条目的     │
│ see_also，替换为归档路径   │
│ (如有替代条目则指向新条目) │
└──────────┘
```

### 归档注意事项

- **永不删除**：归档条目保留在 `_archive/`，可被搜索但不会出现在常规检索结果中
- **反向链接**：替代条目需包含 `supersedes: ../_archive/{旧slug}.md`
- **批量归档**：技术栈升级时，可批量归档同一标签的条目，但每条仍需单独执行 A1-A4
