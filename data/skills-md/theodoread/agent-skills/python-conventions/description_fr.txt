À utiliser lors de l'écriture, de la révision ou de la refactorisation de code Python dans un projet personnel/maintenu par un agent — modélisation des données (Pydantic vs dataclass vs NamedTuple vs TypedDict vs attrs vs msgspec), dates/heures/fuseaux horaires (aware-only, UTC à la limite, replis et écarts DST), gestion des paramètres/secrets, retours anticipés/clauses de garde/fail-fast/EAFP, modularité/DRY/lisibilité/encapsulation, le modèle module-singleton + lazy-property, apatride/immuabilité, structure de test (DAMP vs DRY, portée du luminaire), hiérarchies d'exceptions, hygiène d'ignorance de type, structure de package `src/`-layout, async/concurrency et conventions client/nouvelle tentative HTTP — ainsi que les conventions spécifiques au serveur MCP (discipline de journalisation stdio, gestion des erreurs de limite d'outil, outil orienté LLM docstrings) pour la famille *-polite-mcp. Donne la réponse par défaut par sujet, recherchée par rapport à des sources réputées et aux précédents de la communauté, afin que les choix restent cohérents d'un projet à l'autre au lieu de dériver d'une session à l'autre. Chaque sujet indique s'il remplace l'instinct par défaut d'un modèle ou s'il documente simplement un instinct déjà solide, de sorte que la compétence oriente plutôt qu'elle ne combat le comportement normal de l'agent. Couvre uniquement les conseils de conception/style — pour la configuration de l'outil *checker/linter/formatter/shell-check* de type-checker-linux-setup, consultez plutôt le fichier contribute/quality-tooling.md de power-user-linux-setup.
