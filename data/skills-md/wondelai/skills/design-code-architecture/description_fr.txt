Voyage guidé d'une idée d'application à une architecture délibérée : limites, modèle de domaine, décisions en matière de données et résilience, en prenant uniquement les décisions coûteuses à annuler et en reportant le reste. Orchestre huit compétences phase par phase - architecture propre, conception axée sur le domaine, conception de systèmes, systèmes ddia, philosophie de conception logicielle, release-it, programmeur pragmatique, voie 37signaux - posant des questions à l'utilisateur à chaque point de décision et enregistrant les résultats dans le dossier docs/ du projet (ARCHITECTURE.md, RELIABILITY.md, DESIGN-CODE-ARCHITECTURE-PLAN.md) afin que le voyage reprenne au fil des sessions. À utiliser lorsque l'utilisateur souhaite concevoir l'architecture d'une nouvelle application, choisir des limites et un modèle de domaine avant de la créer, décider d'un monolithe ou d'un microservice, ou demande « comment dois-je structurer cette application ». Si une base de code existe déjà, utilisez Remove-Technical-Debt (anciennement) ou Improvement-code-quality (nouveau prototype) ; si l'idée n'est pas validée, lancez d'abord create-business ou create-app. Pour un framework isolé, invoquez cette compétence directement.
